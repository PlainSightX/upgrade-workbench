# 整套工作台是否比简单工具 Agent 更划算？

两轮比较都使用同模型的合理简单工具 Agent G 和工作台 W；G 可以读源码、运行工具和
修改候选，并非只发送一次提示的裸模型。任务、允许修改范围、独立验收和停止条件预先冻结，
保留首次运行和全部槽位。[结构化结果](result.json)从原任务报告导出，包含 16 个槽位的
候选、任务、源码和协议身份以及三环境验收、token、时间和估算费用。

| 历史比较 | G | W | 可直接支持的结论 |
| --- | --- | --- | --- |
| A2：三项历史迁移、各两次 | 6/6 验收，47 请求，1.190431 USD | 6/6 验收，41 请求，1.745842 USD | 同样通过，W 估算费用高 46.7% |

## 方法与取舍

A2 的两个 SQLAlchemy 案例共享 `execute(str)` 机制，第三项来自 FastAPI/Pydantic 的
缺参错误编码。A5 是另一种机制：移除 `Session.transaction` 后，审计历史回调失效。
W 在 A5 初始获得约 150 KB 完整目标源码、影响点与失败定位；G 初始约 96 KB，
可用工具补读。故 A5 比较的是整套配置，不能归因为 BM25、AST 或某一个角色。

两个反向结果意味着能力与费用依赖任务：不因一个成功案例切换通用默认配置。
这也是使用多机制、保留负结果而非只展示全绿截图的原因。

## 证据边界

- 都是已见/准入开发案例，每臂两次；不是未见泛化、整体成功率或统计显著性的证明。
- 费用来自固定价格与 provider 回传 usage 的估计，不是实际账单；人工工作时间未测量。
- elapsed time 包含审阅等待，不能直接换算人工节省。
- 原修复源码身份与当前发布候选不同；本页是历史结果的精选投影。
- 本页不分发完整历史案例、候选和原始轨迹，不能仅凭此 JSON 重跑全部对照。
  可执行代表案例见 [csvsql](../csvsql/README.md)。私有原件仍有精确恢复记录。

公开投影保留每个原报告的 SHA256 和冻结对象身份，移除账本位置、宿主路径、请求 ID 列表、
自由模型回复和大量日志。哈希用于身份追溯，并不单独证明原运行真实或合同穷尽。
