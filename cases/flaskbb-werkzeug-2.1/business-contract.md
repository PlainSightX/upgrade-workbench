# FlaskBB 管理请求兼容迁移

在固定 Python 3.9 / SQLite 环境中，将 Flask 与 Werkzeug 从 2.0.1 升至 2.1.2。
应用源码来自真实上游提交 cc083eb5f6fee7e7d0da633e327cee69ffd1838d，
这是已合并 SQLAlchemy 1.4 支持的历史版本，不是上轮 SQLAlchemy 案例的候选补丁。

管理员使用浏览器单对象操作及 JSON 批量操作管理用户、用户组和举报。
升级后合法的非 JSON 单对象 POST 不应意外变成 Bad Request。

1. 删除用户、封禁、解封、删除自定义组、标记举报已读及删除举报，保留单对象 URL 的
   非 JSON POST 处理、重定向及数据库持久结果。无需 JSON 请求体，不强制客户端迁移。
2. 六种操作的现有 JSON `ids` 批量行为、响应结构和未选对象隔离必须保留。
3. 保留真实登录/权限校验、禁止删除或封禁自身、标准组删除保护。不绕开授权装饰器。
4. 保留无效 JSON 的 HTTP 400、缺失对象的 HTTP 404、空 JSON 选择的应用级 404。
   不把无效输入变成批量修改。举报显式“全部已读”非 JSON 路由仍处理所有未读对象。
5. 不修改检查、锁文件、环境、身份认证框架或业务表结构；可编辑边界以 manifest 为准。

## 环境与证据边界

两环境统一 Celery 5.2.7、Kombu 5.2.4、Click 8.1.3、amqp 5.0.9、pytz 2021.3，
解决 Flask 2.1 与原 Celery 5.1 的 Click 要求冲突；其余共有包版本一致。
目标环境另含 Flask 2.1 在 Python 3.9 所需的 importlib-metadata 8.7.1 与 zipp 3.23.1。
两组也统一 Flask-Login 0.6.0，避免0.5.0依赖已删除的 `safe_str_cmp` 导致导入失败。
因此旧参照是原始应用源码运行于受控兼容环境，不声称完整复现当年的部署环境。
Flask-Allows 使用已审查的 0.7.1 wheel，不跟随上游浮动 master；未安装完整插件生态。
较大的共有依赖wheel预先按锁文件hash核验，只减少重复下载，不改变版本或安装后的行为。
六个核心路由不依赖外部 worker、Redis 或网络服务。测试仅在隔离 Docker 中执行。

检查沿用上游 TestingConfig、数据库和用户夹具，关闭 CSRF 与 session protection
以直接设置测试身份；真实权限装饰器及业务代码正常执行。结论不涵盖 CSRF/登录安全审计。
静态主题软链接未跟随且未物化，不测试主题资源或重定向后的页面渲染。
详细来源与排除项见 SOURCE.json；本任务为已见仓库的历史后续故障复现，非新发现的上游漏洞。
